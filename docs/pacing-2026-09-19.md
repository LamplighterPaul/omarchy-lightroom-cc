# Photo-drag presentation experiment — 2026-09-19

The custom Proton launcher now defaults to `dxgi.syncInterval = 0` and caps
`dxgi.maxFrameRate` at the destination monitor's refresh rate (120 here; 60 if
unknown). Existing `DXVK_CONFIG` options take precedence. For an upstream
comparison, close Lightroom and launch with `LRCC_PRESENTATION=upstream`.
The runtime remains lightroom-omarchy-proton 11.7-2; this is a launcher change.

## Evidence

Real XTest pointer/button input on a separate GPU-backed Weston desktop,
2880×1800 at 120 Hz, Lightroom client 2832×1692, 192 DPI, same cached lake photo.
Screenshots verified zoomed photo movement and the File popup; private images
are not published. MangoHud 0.8.4 was enabled for both configurations. The photo
view and filmstrip have separate presentation streams; these results describe
active photo presentation, not whole-desktop FPS or measured input latency.

| Continuous drag | Samples | Median ms | p95 ms | p99 ms | Max ms | Frames >16.67 ms |
|---|---:|---:|---:|---:|---:|---:|
| Upstream, warmed 1 | 473 | 17.374 | 19.296 | 21.137 | 31.885 | 71.5% |
| Upstream, warmed 2 | 474 | 17.209 | 19.521 | 21.068 | 24.216 | 70.7% |
| Sync 0, cap 120, 1 | 971 | 8.247 | 10.653 | 12.404 | 56.012 | 0.3% |
| Sync 0, cap 120, 2 | 903 | 8.314 | 15.294 | 18.527 | 26.894 | 2.9% |
| Sync 0, cap 120, 3 | 581 | 8.802 | 28.595 | 31.754 | 49.034 | 30.6% |

Median cadence approximately doubled. The third repeat degraded substantially
in its tail, so this is **not a locked 120 FPS result or a stall fix**. All
intervals inside each measured window are retained, including >100 ms stalls.
The first two upstream startup gestures yielded one/zero samples and are
retained in the source data but excluded from the warmed comparison. Each
10-second continuous gesture loses one second at both boundaries to account
for CSV filename clock precision. Reproduce the table with:

```sh
python3 diagnostics/analyze-pacing.py docs/measurements/20260919-pacing
```

The upstream continuous run used custom GPU compute enabled; the final capped
validation restored the normal auto/compute-disabled preferences. Earlier
single-variable trials with compute enabled in both cases also showed about
17.3 ms → 8.3 ms. Compute preference alone showed no clear benefit. This is
exploratory evidence on a busy desktop, not a fully isolated factorial study.
A 40-second overlapping capped resource sample had median prefix CPU ~99%
(one core), peak ~128%, and median PSS ~2.32 GiB. These are not host CPU/RAM totals.
Do not infer a CPU or GPU bottleneck from those averages alone.

  limits. Host policy was balanced/balance_power with turbo enabled. The recorder
  now includes power policy, CPU policy frequencies and CPU/memory/I/O pressure.
  One-second samples can show context but cannot explain an individual 30 ms stall.
- Reproduce the black flicker with a reliable composited capture. It is unresolved;
  hidden-window X11 capture can itself read black. Colour correctness of the
  existing Direct2D pass-through is also unverified.
- Menu opening/closing was exercised and its popup inspected, but no quantified
  menu-latency improvement is claimed. Startup still needs warm-up.
- One uncapped automated repeat failed to find its window; no crash cause was
  established. The capped instance survived repeated interaction and relaunch.
  The previously documented shutdown threadpool assertion remains unresolved.
- Live Hyprland launch verified workspace 10, 2x, custom Proton, loaded MangoHud
