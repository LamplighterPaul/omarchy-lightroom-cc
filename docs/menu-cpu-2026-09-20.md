# Menu CPU sampling and hybrid-core experiment

Statistical CPU sampling points to Adobe's command-state work as the largest
remaining keyboard-menu cost. A reversible scheduling experiment lowered median
input-to-menu-map latency by about one third. This is not a new default: long
outliers remain, and newly created native graphics threads inherited the tested
main-thread affinity. The desktop keeps the existing rc1 performance profile.

## CPU evidence

The ordinary, immutable `11.7-3-rc1` runtime ran in the private, signed-in Weston
fixture, with 2× scaling and the same photo independently captured before and
after testing. No Wine timing probes, debugger or pixel recorder ran during
sampling. `perf 7.2.3-1` and libpfm were downloaded from the configured official
Omarchy package mirror, signature-verified with pacman-key and extracted into
the application's private tools directory. No system packages, perf permissions
or power settings were changed.

Main Linux thread 2657439 was sampled at a requested 997 Hz with `cycles:u` and
`--clockid mono`. On this hybrid CPU, perf records separate core and atom PMU
events. Samples were filtered to each serial input-submission → X11 MapNotify
interval from `menu-latency.py`. The observer's scheduling is included; mapping
is not proof that pixels reached the physical display.

| Sampled instruction location | Keyboard, 4,114 samples | Mouse, 1,059 samples |
| --- | ---: | ---: |
| AgKernel.dll | 68.1% | 58.4% |
| ntdll.dll | 9.0% | 6.2% |
| ntdll.so | 5.8% | 4.1% |
| mfc140u.dll | 3.5% | 1.9% |
| libc.so.6 | 3.1% | 8.0% |
| win32u.so | 2.5% | 7.6% |

These are sampled instruction proportions, not inclusive costs or exact CPU-time
percentages. In the keyboard sequence, AgKernel accounts for 64.9% of 1,582 core
samples and 70.1% of 2,532 atom samples, so the finding is visible in both PMUs.
Its precise proprietary function names remain unknown. Native Wine syscall
dispatch also appears in the samples; this does not establish that changing it
would preserve compatibility or remove the application-side work.

`diagnostics/menu-cpu-profile.py` resolves anonymously mapped Windows code using
the file-backed PE header, image base and SizeOfImage. It deliberately avoids
attributing arbitrary addresses to the nearest exported function. Outputs contain
module counts, separate PMU counts and 256-byte RVA buckets, without library
contents, photo pixels or credentials. Both full recordings reported zero lost
samples: 9,020 total keyboard samples and 6,292 mouse samples before filtering.

The sampled 60-opening sequences had medians of 65.8 ms for keyboard and 14.4 ms
for mouse. Maximums were 206.2 and 54.1 ms respectively. This supports the earlier
input-path distinction; it does not make mouse openings stall-free generally.

## Scheduling experiment

Local sysfs identifies CPUs 0–3 as core PMU CPUs and 4–7 as atom PMU CPUs. The
default main-thread affinity allowed all eight. Only the private Lightroom main
thread was explicitly restricted with `os.sched_setaffinity`; existing worker
threads were not deliberately changed. No realtime priority, process-wide CPU
restriction, governor or power-limit adjustment was applied.

After an exploratory restricted sequence, four alternating blocks of 40 keyboard
openings ran without perf or pixel capture, on the same process and photo:

| Block | Main-thread CPUs | Median | p95 | Maximum |
| --- | --- | ---: | ---: | ---: |
| A1 | 0–7 | 65.6 ms | 99.5 ms | 153.1 ms |
| B1 | 0–3 | 43.2 ms | 78.2 ms | 179.4 ms |
| A2 | 0–7 | 65.0 ms | 106.3 ms | 253.1 ms |
| B2 | 0–3 | 43.3 ms | 91.1 ms | 228.7 ms |

The median reduction repeats at roughly 33–34%. Maximum latency does not improve
consistently. These serial openings are not a throughput, export or photo-drag
benchmark, and startup/thermal conditions were not independently controlled.

There is an additional scope limitation: a thread audit near the end found 128
workers allowed on all eight CPUs, but two new native `WSI swapchain q/e` threads
had inherited CPUs 0–3. This was not a perfectly isolated main-thread-only change
throughout the experiment. Restoring the main thread alone did not restore those
workers. Both were explicitly restored after verifying their private-process
membership, names and masks; the final audit found all 130 remaining threads
allowed on CPUs 0–7. The normal desktop process was never restricted.

Before promotion, address inheritance and repeat photo dragging, zoom, menu
outliers and worker-heavy operations. Do not restrict the entire application to
four cores on the strength of these menu timings.

## Reproduce attribution

On the owned private fixture, save `/proc/PID/maps` for the process being sampled
and use unique output paths. Record the main thread with:

```sh
perf record --clockid mono -e cycles:u -F 997 -t "$LR_PID" -o keyboard.data -- \
  python3 diagnostics/menu-latency.py keyboard.json --pairs 30 --input keyboard
perf script --ns -i keyboard.data -F time,event,period,ip,sym,dso > keyboard.samples
python3 diagnostics/menu-cpu-profile.py keyboard.samples keyboard.json maps.txt keyboard-profile.json
```

The private perf installation requires its `usr/lib` directory on
`LD_LIBRARY_PATH`. The attribution tool requires the mapped PE files to remain
available and fails on missing files, overlapping image ranges, malformed samples
or non-overlapping clocks. It is an offline diagnostic, not an always-on monitor.

Raw perf recordings, maps and photo captures remain in the private local
measurement directory. This builds on the [aggregate API-cost investigation](menu-cost-2026-09-20.md).
