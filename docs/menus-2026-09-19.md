# Menu latency investigation

The isolated 2880×1800, 120 Hz Weston fixture reproduced menu delays under the
experimental thread-pool candidate. Twenty File menu opens used real Alt+F / Esc
input. The diagnostic Wine patch measures individual synchronous phases and
logs only phase names and durations. Host power settings remained balanced.

| Phase | Median | Maximum |
|---|---:|---:|
| Adobe `WM_INITMENU` callback | 13.411 ms | 147.596 ms |
| Adobe `WM_INITMENUPOPUP` callback | 0.604 ms | 2.548 ms |
| Create popup window | 1.035 ms | 4.226 ms |
| Calculate popup layout | 0.852 ms | 2.930 ms |
| Show popup (`NtUserSetWindowPos`) | 3.843 ms | 235.543 ms |
| Paint popup | 2.212 ms | 11.432 ms |

These phases exclude input arrival, uninstrumented work, and compositor display.
Maxima occurred on different opens and must not be summed. This is attribution
evidence, not an end-to-end benchmark or a performance improvement. Both Adobe
initialization and Wine's popup-show path need investigation; the latter can
also call application code. The whole desktop continued running normally.

[Recorded phase timings](measurements/20260919-menus/candidate-phases.json)
contain all twenty opens, including the stalls. The opt-in source patch is in
the Proton repository at `omarchy/experimental/menu-phase-timing.patch`.

A separate 99 Hz user-cycle profile captured 1,198 samples during another menu
run, including its shutdown. PE mapping attribution placed 382 samples in
CameraRaw.dll across all threads, mostly in workers named `find transparen`.
The main thread had 235 samples in AgKernel.dll and 287 in native or unmapped
code, among other modules. These are sample counts, not percentages of wall
time or proof that background work caused a menu stall. Windows stacks were not
reliably unwound. The private perf file is not published because stack samples
can contain application data.

The profiler was staged locally from signed Arch perf/libpfm packages; both
signatures verified. No system package, scheduling or power configuration was
changed. Unlike an earlier assumption, GDB attaching to our isolated Wine
process also worked with this machine's ptrace scope setting of 1.

## Live user session

A separate 45-second read-only capture on the production window had 41 focused
resource samples. Prefix CPU ranged up to 504.92% (100% means one core), with a
57.26% median. Proportional memory ranged from 1,993.85 to 2,037.28 MiB. The main
thread consumed 13.66 CPU seconds and was often sampled in `ntsync_schedule`.
The capture has no per-click markers, so those waits cannot be assigned to
menus. Runnable queue delay is unavailable with scheduler statistics disabled.

The current runtime continues to use DXVK sync interval 0 and a monitor-based
120 Hz cap. This investigation has not established locked 120 FPS, resolved
black flicker, or justified a global priority/power change.

## Power and resource-limit audit

At 20:46–20:48 CEST, the live process could run on all eight logical CPUs. Its
main thread used normal scheduling and nice 0. Eight named background disk/log
workers used nice 19. Every cgroup ancestor exposed unlimited CPU quota and
unlimited memory where those controls were present; recorded CPU throttling
counters were zero. No VM-style CPU or RAM allocation limits were found.

The machine had changed to **performance** mode since the earlier balanced
capture. CPU energy preferences were all `performance`, turbo was enabled, AC
power was online, and power-profiles-daemon reported no degraded condition.
This investigation did not change that policy. The Intel Xe render GT's configured
maximum was 2500 MHz, matching its exposed RP0 value. Instantaneous clocks alone
do not show whether a stall was GPU-bound or power-limited.

The read-only `measure` recorder now includes main-thread affinity/nice/policy,
cgroup ancestor limits, Xe GPU clocks and cumulative thermal-throttle counters.
Compare counter changes over the same interaction. The verification recording
had no focused Lightroom samples and no new thermal-throttle events: this
validates collection, **not** performance under load.

A separate all-cores / performance-cores / all-cores menu comparison was
interrupted by the focus guard during its middle phase. It is incomplete and
supports no affinity recommendation. No affinity change touched the production
Lightroom process. The deliberate 120 Hz presentation cap remains in place.
