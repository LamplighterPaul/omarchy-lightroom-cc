# Frame limiter comparison — 2026-09-19

A/B/A: DXVK 120 FPS → MangoHud 120 FPS late limiter → DXVK 120 FPS.
All used sync interval zero, custom Proton 11.7-2, the same independent prefix,
auto/compute-disabled preferences, cached lake photo, 2x scaling, 2832×1692
client and GPU-backed Weston 120 Hz fixture. The normal desktop Lightroom
remained idle. A guard would stop the isolated prefix if the user focused their
Lightroom; it did not fire during this run.

Each launch warmed for 60 seconds, entered photo view, and performed an unscored
10-second drag before three scored continuous drags. Before/after screenshots
confirmed the photo and zoomed view; private images are not published. Both
configurations loaded the same MangoHud release and displayed the same overlay.
Only the limiter changed. No power or priority setting changed.

MangoHud produced tighter cadence around the 8.33 ms target. It did not eliminate
all long frames. One short A/B/A test on one photo is not a general latency,
flicker, menu responsiveness or native-parity result. Keep it opt-in until the
normal Hyprland session and other interaction types confirm the benefit.

Raw CSVs and gesture windows are in `measurements/20260919-limiters/`. As in the
previous report, the analyzer trims one second at each boundary for filename
precision and retains every interval inside the remaining span, including
stalls. It measures photo presentation cadence, not physical display latency.

```sh
python3 diagnostics/analyze-pacing.py docs/measurements/20260919-limiters/mango120
```

## Launcher integration validation

The optional profile was installed and exercised with two more drags and menu
open/close input. Its final screenshot showed 120 FPS / 8.3 ms, the 28px HUD and
process memory label. MangoHud requires `read_cfg=1` when environment options are
present; the launcher sets it so the logging destination, hotkey and HUD scale
remain intact. Unit coverage checks the missing-layer failure, one active cap,
config-file preservation and hidden/visible HUD behavior.

The close shortcut and an explicit WM_CLOSE request did not promptly terminate
the test process. This does not establish a new limiter regression, but also
cannot certify clean shutdown. The older threadpool assertion remains an open
stability issue. The normal desktop instance was not restarted or reconfigured.
