# Menu API cost and explicit photo-view measurements

The diagnostic build adds aggregate counters around four Wine menu API families
during the previously identified posted-character-to-next-poll interval. The
same interval records wall time and main-thread CPU time. It changes no menu
state, input ordering, rendering, authentication or desktop settings.

Across 21 keyboard openings (one exploratory opening and a 20-opening serial
photo-view run):

| Measurement | Median | Maximum |
| --- | ---: | ---: |
| Whole pre-poll interval | 45.018 ms | 115.631 ms |
| Main-thread CPU during interval | 42.960 ms | 105.222 ms |
| 22,000 menu-information API bodies | 1.309 ms | 3.795 ms |
| 458 EnableMenuItem API bodies | 0.019 ms | 0.027 ms |

Counts were identical in all 21 intervals; CheckMenuItem and DrawMenuBar counts
were zero. The instrumentation includes timer overhead but excludes the
Windows/Unix call boundary and does not cover every API or runtime function.
Consequently it cannot attribute all remaining CPU time to Adobe code alone.

To check boundary overhead, `diagnostics/menu-api-bench.c` creates 458 synthetic
menu items and runs 22,000 queries per method over five passes. Complete call
times were 1.356–1.400 ms for GetMenuItemID, 1.386–1.465 ms for GetMenuState,
1.692–1.740 ms for GetMenuItemInfoW state/ID, and 1.962–2.125 ms with text copying.
This covers representative API entry/exit costs; it does not reproduce the
application's exact arguments, menu hierarchy or processing between calls.
It does not support menu-API caching or input reordering as the next fix.

## Correct the recorder's view preparation

Escape while no menu is active can leave the photo for the grid. The old
recorder cleared navigation with Escape twice without subsequently setting an
explicit view. Calling D immediately before that recorder could also leave a
view transition in flight during the first timed opening. Prior results remain
observations of those sequences, but cannot establish a settled photo-view or
pure first-menu cost.

`menu-latency.py` now selects `--view photo` (default) or `--view grid` after
clearing navigation, records that preparation and waits two seconds before
opening the first menu. A delay alone is not proof of an idle application.
Private screenshots in this run independently confirm the signed-in photo at
2× before the test and the same photo after keyboard and mouse menu sequences.
Two Escapes after an open keyboard menu preserved this view in that check.

The new photo-view series still contains warm keyboard delays and occasional
longer events. They are retained in the numeric receipts rather than discarded
as outliers. This diagnostic work does not promote a new performance patch.

## Validation and artifacts

The incremental Proton SDK build completed. Its separate diagnostic runtime,
`lightroom-omarchy-proton-menu-cost`, changes only x64 Unix win32u relative to
rc1. Actual menu openings, screenshots and normal Ctrl+Q were exercised; the
private Lightroom process exited. The synthetic benchmark compiled with
`-O2 -Wall` and exited successfully. The existing desktop session remains on
the working performance profile, with no debugger attached.

[Numeric results](measurements/20260920-menu-cost/) contain no photos or
credentials. The Proton fork holds `omarchy/experimental/menu-api-cost.patch`
and usage notes. Full logs and screenshots remain private. The remaining
keyboard gap is predominantly CPU work outside the measured menu API bodies;
the next useful investigation is application command-state processing and its
other runtime costs, rather than assuming a GPU or scheduling limit.
